## 2. 为什么内置分类「可改名不可删」

四个内置分类（登录 / 银行卡 / 证件 / 笔记）是 `seedBuiltinCategoriesIfNeeded()` 用**固定 id** 写进去的：

```kotlin
builtin_login / builtin_card / builtin_id / builtin_note
```

固定 id 不是为了好看 —— 分类名是**加密字段**，AAD 是 `分类id|name`。如果 id 每次安装都变，那么从备份恢复的数据里所有分类名都解不开。

由此推出两条规则：

| 操作 | 内置 | 自建 | 理由 |
|---|---|---|---|
| 改名 | ✅ 允许 | ✅ 允许 | 复用原 id，AAD 不变，只换密文 |
| 删除 | ❌ 拒绝 | ✅ 允许 | 删了之后下次启动 `seed...` 又建回来，用户会看到"删了又出现"的鬼故事 |

`deleteCategory()` 里第一行就是 `if (category.builtin) return false`，UI 层同时把内置项的删除按钮置灰显示"内置不可删"——**两道防线**，因为 UI 状态可能因重组时序不稳。

## 3. 删分类不删条目

三级处理，顺序不能改：

```kotlin
db.withTransaction {
    entryDao.clearCategory(id)   // ① 先摘掉引用
    categoryDao.delete(id)       // ② 再删分类行
}
```

**为什么先清引用再删行**：`entries.category_id` 上有外键（`onDelete = SET_NULL`）。理论上删分类会让 SQLite 自己把引用置空——但那张外键要 `PRAGMA foreign_keys = ON` 才生效，而 Room 的 `SupportSQLiteOpenHelper` 默认**不保证**它开着。

所以这里**不把正确性押在 PRAGMA 上**，显式 `UPDATE`。代价是两句话，收益是"分类删了、条目还在"这件事在任何 SQLite 配置下都成立。

**绝不 `DELETE FROM entries WHERE category_id = ?`** —— 分类只是个标签，删标签不该删数据。UI 的确认对话框会写明"有 N 条会变成未分类"。

## 4. 排序：整表重写 sort 为 0..n-1

`moveCategory(id, delta)` 的实现不是"改两个 sort 值"，而是：

```kotlin
val swapped = Reorder.swap(rows, index, index + delta) ?: return false
db.categoryDao().upsertAll(swapped.mapIndexed { i, c -> c.copy(sort = i) })
```

理由：如果只交换两个 `sort` 值，只要历史上有过一次重复值（比如并发新建），排序就会变得不确定。整表重写成 `0..n-1` 后，`ORDER BY sort ASC` 的结果永远可复现。

代价是 n 次 UPDATE，n 是分类数量（个位数到几十），可以接受。

`Reorder.swap` 返回 null 就直接 `return false` —— 上层据此知道"已经在头/尾"，不需要自己算边界。这也是把交换抽成纯函数的主要原因：**边界情况在 Room 上测不了**（需要 instrumentation，慢且难写），抽出来就能毫秒级覆盖 11 个用例。

## 5. 自定义字段：id 必须跨次编辑稳定

这是 W5 最容易出错的地方。

自定义字段的密文 AAD 是：

```
字段id|cf_label      ← 名称
字段id|cf_value      ← 内容
```

所以：

| 情况 | 结果 |
|---|---|
| 编辑时保留原 `id` | 旧密文能解开 ✅ |
| 编辑时生成新 `id` | 旧密文全部解不开，表现为"字段内容变乱码/抛完整性异常" ❌ |

因此 `EntryEditScreen` 里加载时是：

```kotlin
customFields = detail.customFields.map {
    CustomFieldDraft(id = it.id, label = it.label, value = it.value, type = it.type)
}
```

**不能用 `CustomFieldDraft(label = ..., value = ...)`** —— 那会走默认的 `id = null`，保存时生成新 id，用户一编辑就丢内容。

新增一行时 `id = null` 是正确的：新字段没有旧密文，保存时分配 id 即可。

写库时 `deleteForEntry(id)` 先删全部再插入，所以字段被删掉是干净生效的。

## 6. 两种字段类型

| type | UI | 列表显示 |
|---|---|---|
| `text` | 明文 | 明文 |
| `secret` | 明文（编辑时可见） | `••••••••` |

只有两种，没有 `multiline`。

`value` 字段无论类型**都加密存储**——`type` 只决定 UI 是否打码，不影响加密。这一点容易误解：有 `type` 不等于 `text` 就明文落库了，全部一样加密。

为什么不做 `multiline`：备注（`notes`）已经覆盖了长文本需求，自定义字段的定位是"短小、多条、有名字"，再加一种类型只会让 UI 更复杂而没有实际收益。

### 顺手修掉的一个旧 bug：编辑会清掉收藏

`EntryEditScreen` 提交时原本写死 `favorite = false`。这意味着**用户每次改个错别字保存，收藏标记都会被清掉**，而且用户完全不知道发生了这件事——列表里的 ★ 就这么消失了。

修法三步：

1. 加 `var favorite by remember { mutableStateOf(false) }`
2. 编辑加载时 `favorite = detail.summary.favorite`
3. 提交时 `favorite = favorite`（不再是字面量）

顺带在分类 chip 下面加了一个「☆ 收藏 / ★ 已收藏」的 `FilterChip`——这个字段之前在 UI 上**完全没有入口**，只有详情页顶部一个只读的 ★。现在它第一次能被用户设置。

> 这类 bug 的共性：**字段写死而非透传**。凡是「编辑页提交」的地方，都要问一句"哪些字段我没让用户改、但也没把原值带回去"。
