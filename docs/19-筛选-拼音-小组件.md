## 2. ① 分类筛选

### 为什么是"筛选项"而不是"下拉菜单"

列表页之前只有一个搜索框。用户要"看我所有的银行卡"，得自己去想关键词
（"卡"？"银行"？），而分类本来就是他自己分好的。

用一排横向 chips 而不是下拉菜单，理由是**可见性与点击成本的差别**：

| | 下拉菜单 | 横向 chips |
|---|---|---|
| 看见有哪些分类 | 要先点开 | 直接摊在屏幕上 |
| 切换分类 | 点开 → 选 → 收起（3 下） | 1 下 |
| 当前在哪个分类 | 收起后看不见 | 一直在 |

### 三个设计决定

**只列出有内容的分类。** 空分类不出现 —— 16 个分类平铺出来是 3 到 4 行，
但多数人常用的就三五个，把空的全列出来等于每次都要在一堆零里找那个数。

**先筛选、再搜索。**

```kotlin
val current = filter
val scoped = when (current) { ... }       // 先按分类收窄
val result = if (query.isEmpty()) scoped   // 再在收窄结果里搜
             else scoped.filter { ... }
```

顺序反过来的话，"在登录分类里搜 taobao"会先对全表做一遍匹配再筛分类，
白做一次全量计算。记录多了以后这个差别能感觉到。

**搜索索引的键从下标改成 id。** 原来 `searchIndex` 是 `List<String>`，
`filtered[i]` 靠下标对齐 `items[i]`。一加筛选，`filtered` 的下标和 `items`
的下标就不是一回事了，于是搜到的东西和显示的东西错位。改成
`Map<String, String>`（id → 搜索串）之后不可能再错。

### 空态的三种情况

| 情况 | 文案 | 附带动作 |
|---|---|---|
| 有搜索词 | 没有匹配的条目 | 换个关键词试试 |
| 有筛选 | 这个分类下还没有记录 | 「看全部记录」按钮 |
| 什么都没有 | 还没有记录 | 「新建第一条」按钮 |

原来只有一句"没有匹配"。加了筛选之后必须区分 —— 否则用户在「银行卡」分类下
看到"没有匹配的条目"，会以为自己的记录丢了。

## 3. ② 拼音首字母

### 词库从哪来（这一节是重点）

做"拼音搜索"通常要内嵌一张几万字的映射表（两三兆的数据库或一堆数组）。
这里没用。

**GB2312 的一级汉字区（0xB0A1–0xD7F9）本身就是按拼音字母序排列的**，
共 3755 字。也就是说，只要知道每个声母占多少字，就能反查任意一个字的声母。

用脚本遍历整个区间做了两件事：

1. 确认总数 3755、确认 23 个锚点字（啊 / 八 / 擦 / 搭 / 蛾 / 发 / 噶 / 哈 /
   击 / 喀 / 垃 / 妈 / 拿 / 哦 / 啪 / 期 / 然 / 撒 / 塌 / 挖 / 昔 / 压 / 匝）
   单调递增 —— 排序假设成立
2. 生成 24 个分界下标（0 与每个声母的首字位置，末尾补 3755）

```
0, 42, 220, 453, 637, 659, 784, 939, 1120, 1415, 1515, 1763,
1914, 1995, 2003, 2125, 2282, 2341, 2627, 2783, 2903, 3126,
3432, 3755
```

23 个声母 `abcdefghjklmnopqrstwxyz`（GB2312 一级汉字里没有 i / u / v 开头）。

单字求声母的完整过程：

```kotlin
val bytes = ch.toString().toByteArray(gb2312)   // GB2312 编码
if (bytes.size != 2) return NONE                 // 非 GB2312 汉字
val hi = bytes[0].toInt() and 0xFF
val lo = bytes[1].toInt() and 0xFF
if (hi !in 0xB0..0xD7 || lo !in 0xA1..0xFE) return NONE
val index = (hi - 0xB0) * 94 + (lo - 0xA1)       // 区内平铺序号
val block = BLOCK_STARTS.binarySearch(index)     // 二分找落在哪个声母段
```

**代价**：`Charset.forName("GB2312")` 在某些裁剪过的 ROM 上可能取不到。
取不到就整功能降级（`gb2312 == null` → 所有汉字返回 NONE），
搜索退化成"只按原文匹配"—— 功能变少，但不会崩。

### 三条明确写死的边界

| 边界 | 表现 | 为什么接受 |
|---|---|---|
| **只有首字母，没有全拼** | `zfb` 能搜到支付宝，`zhifubao` 不能 | 首字母是"手指头最短路径"；全拼要两倍长的输入，而中文用户打拼音本来就是打首字母 |
| **只认 GB2312 一级汉字** | 生僻字、繁体、日文汉字没有首字母 | 一级字覆盖日常用字 99% 以上；这些人名/生僻品牌仍能按原文搜到 |
| **多音字取 GB2312 排的那个音** | 「行」→ x（不是 h）、「重」→ z | 没有词库就无法根据上下文判断读音。固定取一个至少是**稳定**的：用户搜几次就知道该打哪个字母 |

### 搜索键怎么拼

```kotlin
fun searchKey(raw: String): String =
    Normalize.forSearch(raw) + " " + initials(raw)   // 首字母为空时省掉空格
```

用空格分隔原文与首字母，和 `EntrySummary.searchText()` 用 `\u0001` 是同一个理由：
防止跨字段意外拼出命中（"淘宝"的尾字 + "宝支付"的首字拼成某个词）。

### 验证

29 组抽查全对：淘宝→tb、支付宝→zfb、京东→jd、微信→wx、银行→yh、
证件→zj、会员→hy、笔记→bj、其他→qt、登录→dl、保险→bx、车辆→cl。

唯一"不符"是「行」→x（预期 h），属上表的第三行，不是 bug。

## 4. ③ 桌面小组件

### 它省掉的那几步

| | 原来 | 有小组件之后 |
|---|---|---|
| 1 | 解锁手机 | 解锁手机 |
| 2 | 找并打开账号本 | — |
| 3 | 在列表里找到那一条 | — |
| 4 | 点进去 | 点桌面上那一行 |
| 5 | 点「复制密码」 | —（自动复制） |

从 5 步降到 2 步。而且**不用回忆它叫什么** —— 名字就写在桌面上。

### 为什么不直接读数据库

`AppWidgetProvider.onUpdate` 是 BroadcastReceiver 主线程，约 10 秒预算。
想读库得：取口令 → 打开 SQLCipher（首次解页几十到几百毫秒）→ 后台线程查 →
关闭并清零口令。每一步都可能失败，而**失败的表现是桌面上一块空白，没有任何提示**。

所以改成：**主进程在数据变化时把前三条写进 SharedPreferences**，widget 只读 prefs。
同步、毫秒级、不碰数据库、不会因为钥匙缺失而变空白。

列表页本来就有排好序的 `items`（收藏 → 最近使用 → 更新时间），
`take(3)` 正好是"最常用三条"。

**缓存里不放密码。** 只有标题、账号、首字。这与 `entries` 表的存储等级一致
（本项目已选明文方案），但密码一旦进 prefs 就多了第二份拷贝，
而 widget 根本用不到它。

### 为什么点击不是直接复制

Android 10 起，**后台进程写剪贴板会被系统静默丢弃**。BroadcastReceiver 正是后台进程。
所以"widget 里直接复制"在没有前台窗口时根本不生效 —— 看起来像是点了没反应。

只能：`vaultbook://copy/<id>` 拉起应用 → 前台复制 → 停在详情页让用户看见复制了什么。

`PendingIntent` 的 `requestCode` 用行号（0..2），`FLAG_UPDATE_CURRENT | FLAG_IMMUTABLE`；
不同条目靠 data uri 里的 id 区分。

### 布局为什么不能 include

RemoteViews 只支持一小撮控件，而且 `<include>` 覆盖 id 只会改根节点 ——
行内的 `widget_row_title` 在 3 份副本里会撞成同一个 id，`findViewById` 永远只拿到第一份。

所以三行是**逐行展开、id 各自独立**的（`widget_row1_title` / `widget_row2_title` /
`widget_row3_title`）。行数写死 3，不足时由 Provider `setViewVisibility(GONE)`。

`MAX_ROWS = 3` 必须与布局一致，两处都写了注释提醒。

### 为什么用 commit 而不是 apply

写完缓存会立刻发广播要求重绘，而广播与重绘可能在另一个进程完成。
`apply` 是异步落盘的，对方有可能读到旧值 —— 表现为"新建了一条，桌面还是老样子"。
一次几十条记录的 JSON，同步 IO 代价可以忽略，所以 `@SuppressLint("ApplySharedPref")` 保留 `commit`。

## 5. 本阶段修掉的问题

| 问题 | 现象 | 修法 |
|---|---|---|
| 搜索索引按下标对齐 | 加筛选后搜到的东西和显示的不一致 | 改 `Map<String, String>`，id 做键 |
| `filter` 是委托属性 | 编译错：`Smart cast to 'QuickFilter.Category' is impossible` | `val current = filter` 后再 `when` |
| `context` 声明在用法之后 | 编译错：`Unresolved reference 'context'`（两处） | 单独取一份 `widgetContext` |
| 小组件缓存首次写空 | 打开应用瞬间桌面闪一下空态 | `cachePrimed` 标记，第一次空列表跳过 |
| `MAX_ROWS` 与布局不一致 | 缓存 4 条但只有 3 行 | 统一改 3，两处都加注释 |
| `ApplySharedPref` ×2 警告 | lint 不为 0 | `@SuppressLint` + 写明为什么必须 commit |
| `targetCellWidth/Height` 只支持 API 31+ | lint `UnusedAttribute` ×2 | 加 `tools:targetApi="31"` |

5. 搜 `tb` → 应命中「淘宝」
6. 搜 `yhk` → 命中「银行卡」这类（首字母要连续）

**桌面小组件**

7. 长按桌面空白 → 组件 → 找到「账号本」→ 拖到桌面（4×2）
8. 应显示最常用三条 + 右上角「＋新建」
9. **点某一行 → 应用打开到详情页，屏幕下方弹「密码已复制」**
10. 回到桌面 → 该条应仍在列表顶部（`last_used_at` 更新）
11. 在应用里新建一条 → 回桌面，widget 应在几秒内刷新出这一条

**排查表**

| 现象 | 先看 |
|---|---|
| 组件列表里找不到账号本 | 是否覆盖安装成功；某些启动器要重启才刷新组件列表 |
| 组件一片空白 | 先在应用里把列表滑一下（触发写缓存），再看 |
| 点了某一行没复制 | 详情页是否弹出「密码已复制」；若弹出但剪贴板是空的，是 ROM 拦截了写剪贴板 |
| 组件内容不更新 | 回到应用列表页停留 1 秒（触发刷新） |
| 拼音搜不到 | 该字是否生僻字/繁体；换原文搜索试试 |

## 7. 已知限制

| 限制 | 说明 |
|---|---|
| 小组件固定三行 | RemoteViews 不能动态加行；想显示更多要再做一套 4×4 布局 |
| 小组件不自动刷新 | `updatePeriodMillis=0`，只在应用里数据变化时刷新。系统最小周期是 30 分钟，那个粒度没意义 |
| 拼音只有首字母 | 见 §3 的三条边界 |
| 筛选不跨页记忆 | 退出应用重进回到「全部」（没有持久化筛选状态） |
| 小组件缓存是明文 | 与主库同等级；不含密码 |
