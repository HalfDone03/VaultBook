## §2 W3 要解决的三个问题

### 问题一：有一半登录页，系统根本不会通知本应用

W2 的自动填充依赖 `AssistStructure` 里每个输入框的 `autofillId`。而下面这些页面**不提供**：

- Flutter / React Native / Unity 自绘的输入框；
- 游戏内嵌 WebView；
- 部分银行 App 的自定义安全键盘（连密码框都不是 `EditText`）。

没有 `autofillId`，系统不会发起填充请求，`onFillRequest` / `onSaveRequest` 一次都不会来。
**唯一的出路是直接读无障碍节点树。**

### 问题二：捕获必须无感，但无感 = 用户不知道

自动填充那条路有天然的用户动作（点「保存」）。无障碍这条路，用户在别的应用里点登录，
本应用全程不露面。所以必须有通知，否则功能等于不存在。

### 问题三：很容易抓到不该抓的密码

节点树里**到处都是密码框**：注册页、改密页、支付密码、锁屏密码、输入法的候选栏。
无差别抓取的后果比"抓不到"严重得多 —— 会覆盖掉本来能用的那条记录。

## §3 触发时机：只在点「提交」的那一瞬间读屏

这是整个 W3 最重要的设计决定。

```
用户输入账号密码
    ↓  TYPE_VIEW_TEXT_CHANGED（每敲一个字都来）
    ↓  节流 250ms，只刷新一份"最近看到的表单"快照，不落库
    ↓
用户点「登录」
    ↓  TYPE_VIEW_CLICKED，且按钮文案命中提交词
    ↓  立刻读根节点树（此刻页面还没跳走，密码框里还有值）
    ↓  置信度仲裁 → 落库（锁定进队列 / 解锁进加密库）
    ↓  发通知
    ↓
页面跳转（TYPE_WINDOW_STATE_CHANGED）
    ↓  若上面那步没抓到（WebView 按钮不带文本），用 10 秒内的缓存快照补一次
```

为什么不在每次文本变化时就抓：

- **隐私**：持续读屏等于把用户输入的每一个字符都经过本应用，而绝大多数与账号密码无关；
- **性能**：`rootInActiveWindow()` + 遍历上千节点，每敲一个字跑一次会让输入框卡顿；
- **准确**：用户可能在输错后删掉重输，只有"点提交"那一刻的值才是真正要用的。

节流窗口 250ms、缓存快照存活 10 秒、两次落库最小间隔 3 秒 —— 三个数字都在
`CaptureAccessibilityService` 的 companion 里。

## §4 域名从哪来：地址栏，而且必须允许"找不到"

`AssistStructure` 有 `getWebDomain()`，无障碍**没有**。唯一线索是地址栏节点的文本。

| 情况 | 地址栏文本 | 结果 |
|---|---|---|
| 已加载完、失焦 | `taobao.com` | ✅ 认得出 |
| 正在编辑 | `https://taobao.com/login?x=1` | ✅ 剥掉协议与路径 |
| 新建标签页 | `搜索或输入网址` | ❌ null |
| 搜索结果页 | `淘宝网 - 淘！我喜欢` | ❌ null，**且绝不猜** |
| 账号框填了邮箱 | `alice@example.com` | ❌ null（含 `@` 一律拒绝） |
| 中文域名 | `例子.中国` | ❌ null（TLD 非纯字母） |

`BrowserHosts` 的判定是**格式强校验**，不是"尝试解析"：

1. 含 `@` → 直接拒绝（这是最重要的一条，见下）；
2. 剥协议 / userinfo / 路径 / 查询 / 片段 / 端口；
3. 必须含点号，每段以字母数字开头结尾，顶级标签必须**纯字母 2–24 位**；
4. 通过后才交给 `Normalize.hostFromUrl` 做 eTLD+1 归一。

> **为什么顺序不能反**：`Normalize.hostFromUrl` 对没有点号的任意文本会**原样返回**
> （见 `core/util/Normalize.kt:66`）。直接拿它判断"这是不是域名"，`淘宝` 会被当成合法 host。
> 所以必须先自己校验格式，再交给它归一。

> **为什么 `@` 必须拒绝**：账号框里填邮箱是极常见的操作，而那些输入框的文本也会进候选列表。
> 不拦的话 `alice@example.com` 会被剥成 `example.com` —— 用户明明在登录淘宝，
> 记录却被挂到 `example.com` 名下。这是能导致"把密码填到别人网站"的事故。

拿不到 host 时降级为**只按包名匹配**（`packageNorm = 包名`），功能仍然可用，
只是同一个浏览器里的不同网站会被当成同一来源。绝不根据页面标题猜域名。

## §5 字段识别：三级信号 + 树序兜底

| 优先级 | 信号 | 可靠性 | 说明 |
|---|---|---|---|
| 1 | `isPassword` 标志位 | 最高 | 系统给的，不受文案影响 |
| 2 | 可编辑性 + 文案关键词 | 中 | hint / contentDescription / 类名 |
| 3 | **树序** | 兜底 | 密码框之前最后一个可编辑框 = 账号框 |

Flutter / RN 页面的 `viewIdResourceName` 一律为空，类名可能是一堆 `android.view.View`，
所以第 3 条是这类页面唯一的办法。用树序而不是几何位置，是因为无障碍节点树没有坐标，
只有先序顺序 —— 而先序顺序在网页表单里恰好等于视觉上的从上到下。

### 刻意排除：搜索框

搜索框也是可编辑框，也出现在几乎每个电商首页。不排除的话：
用户在淘宝首页点搜索框 → 输入「连衣裙」→ 点「搜索」→ 会被当成一次登录，
库里多一条「账号=连衣裙，密码=（空）」的垃圾记录。

所以 `SEARCH_HINTS`（search / query / 搜索 / 查询 / 筛选…）的优先级**最高**，
命中即判为"不是账号框"，连 `password` 字样都压不过它。

### 另一条坑：`name` 不是账号

`USERNAME_HINTS` 里刻意**不含**单独的 `name`。`AUTOFILL_HINT_NAME` 指的是**真实姓名**，
常见于收货地址表单。拿它当账号框，会把「张三」填进登录框的账号位置。

（这条和 W2 的 `AutofillHints` 是同一个陷阱，两处都写进了注释。）

## §6 为什么跳过注册页

**判定**：页面上有 2 个及以上密码框（`looksLikeRegistration`）。

**理由**：注册页的密码是"新设的"，用户很可能还要过验证码、勾协议、等审核，
中途失败就作废了。把它当登录凭据存起来，下次自动填充会填一个**从来没生效过的密码**，
用户会以为密码管理器坏了。

**代价**（写在这里以便日后决策）：在某个 App 里注册账号时，第一遍不会自动记下来。
用户需要手动添加，或者注册完再登录一次让它抓到。

取舍原则：**宁可漏记（用户能手填），不要记错（会覆盖掉能用的那条）。**

## §7 通知

三个实现要点：

1. **小图标用 `android.R.drawable.ic_lock_lock`**。本工程刻意没有自定义 launcher 图标
   （避免缺 drawable 让 AAPT 直接失败），通知小图标同理。系统图标在 API 26+ 都存在。
2. **必须检查权限**。API 33+ 没有 `POST_NOTIFICATIONS` 时 `notify()` 抛 `SecurityException`，
   而调用方是无障碍服务 —— 抛出去会被系统判为服务异常，直接影响自动填充是否还愿意被调用。
   所以先 `areNotificationsEnabled()`，再 `runCatching` 兜底（个别 ROM 行为不一致）。
3. **`IMPORTANCE_LOW`**：要出现，但不要响。用户正在输密码，此时"叮"一声是纯干扰，
   而且会暴露"这个手机在记东西"。

通知点击带 `EXTRA_OPEN_PENDING`，`MainActivity` 用**递增计数**而不是布尔值传递意图：
布尔值连续两次置 `true` 不会触发 Compose 重组，用户在待确认页按返回后第二次点通知就失效了。

保险库锁着时这个意图会**保留到解锁之后** —— 否则用户点「已捕获 3 条」进来，
看到的是解锁页，解锁后又回到列表页，通知看起来就像没生效。

## §8 真机验证

### 前置

1. 装 debug 包，解锁一次保险库，建一条记录；
2. 系统设置 → 无障碍 → 找到「账号本 · 增强捕获」→ 打开；
3. 系统设置 → 通知 → 允许「账号本」发通知（API 33+ 会在解锁后弹一次请求）。

### 六步走一遍

| # | 操作 | 预期 |
|---|---|---|
| 1 | 用 Chrome 打开任意网站，在登录页输账号密码，点「登录」 | 状态栏出现「已捕获 1 条待确认」 |
| 2 | 回到账号本 → 点右上角铃铛 | 看到那条捕获，站点名是域名，账号已填 |
| 3 | 点「保存」 | 进了保险库；再次去那个网站，账号框能弹候选 |
| 4 | **先锁屏 1 分钟**，重复第 1 步 | 通知照样出现（锁定期间的捕获走 Keystore 队列） |
| 5 | 解锁账号本 | 待确认列表里出现第 4 步那条（队列已自动搬进库） |
| 6 | 让账号本保持锁定，`adb shell run-as com.yg.vaultbook.debug ls files/` | 能看到 `pending_captures.json`，解锁后该文件消失 |

### 排查表

| 现象 | 原因 | 处理 |
|---|---|---|
| 完全没有通知，也没有待确认 | 无障碍服务没开 / 被系统"优化"关掉 | 检查设置里服务状态；国产 ROM 还要在电池优化里放行 |
| 有通知但站点名是"未知站点" | 该浏览器不在白名单 | 按 `docs/08` §4 的表核对地址栏文本，或改用手动添加 |
| 抓到了但账号为空 | 页面账号框没有文案，且不在密码框之前 | 属已知局限（见 §9），手动补 |
| 在某个 App 里注册时不抓 | 有意的，见 §6 | 注册完登录一次即会被抓到 |
| 每次登录都多一条重复记录 | `host_norm` 与 `package_norm` 都为空 | 检查该页面是否既无白名单浏览器也无包名（正常不会） |

## §9 已知缺失与边界

| 项 | 说明 | 计划 |
|---|---|---|
| 无"立即确认"提示条 | 现在只有通知，要用户主动点。做应用内浮层需要后台启动 Activity 权限，代价太大 | P2 评估 |
| 多账号页面不能手动指定 | 识别只取一个账号框；同一站点多套账号仍要去待确认页人工挑 | P2 |
| 页面标题可能截断 | 标题取最浅节点的前 80 字 | 可接受 |
| 小众浏览器只按包名匹配 | 白名单外的浏览器，同浏览器内不同网站会被当成同一来源 | 可按需扩充 `BrowserHosts.PACKAGES` |
| 部分 ROM 屏蔽密码框文本 | 无解，系统级限制；表现为"抓到了但密码为空"，实际不会落库 | — |
| 自定义安全键盘 | 密码框不是 `EditText`，节点树里根本没有密码 | 无解（这正是安全键盘的目的） |
