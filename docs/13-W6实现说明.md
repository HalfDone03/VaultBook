## §2 为什么不直接加密数据库文件

最直觉的做法是：把 `vault.db` 整个文件读出来，用备份密码再加密一层。它有几个问题：

| 做法 | 问题 |
|---|---|
| 直接拷 `vault.db` | 文件里的口令是派生密钥，拷走也没用；而"再加密一层"需要先拿到明文页 |
| 用**主密码**加密备份 | 导入时必须知道原主密码；用户改过主密码的旧备份就废了。而且备份密码与主密码相同，等于把"一个密码保护两处"捆在一起 |
| 导出**明文快照 + 独立备份密码** | ✅ 采用 |

导出快照意味着：备份文件与主密码解耦（换主密码后旧备份仍可导入），且导入时是走正常的 `createEntry`/`updateEntry` 路径，所有 AAD、强度计算、分类外键都按当前版本重新算一遍 —— **不存在"旧格式密文被塞进新库"的可能**。

代价：导出那一刻，全部密码同时以明文存在于内存里。这是全工程唯一一次。所以 `BackupScreen` 里的顺序被刻意固定为：

```
读取快照（解密全部密码） → 立刻 launch 系统保存对话框 → 用户选完位置 → 写文件 → clearSecrets
```

而不是「先让用户选位置，再读快照」—— 后者在用户对着保存对话框发呆的十几秒里，内存一直躺着一份明文。

## §3 备份文件格式

```
偏移   长度      内容
0      4        魔数 "VBCK"（0x56 42 43 4B）
4      1        容器版本（当前 1）
5      2        KDF 参数长度（大端 16 位）
7      kdfLen   KDF 参数（UTF-8 文本，形如 algo=pbkdf2-sha256;iter=210000;salt=…;len=256）
7+kdfLen  12    GCM IV
…      密文     AES-256-GCM(payload) + 16 字节 TAG
```

### AAD 覆盖**整个文件头**

这是本格式最关键的一个决定。GCM 的 AAD 是"参与认证但不加密"的数据。我们把它设为 `bytes[0 .. 7+kdfLen]`，也就是魔数 + 版本 + kdf 参数全长。

如果不这么做，攻击者可以：

1. 拿到你导出的备份文件；
2. 把文件头里的 `iter=210000` 改成 `iter=1`（一个字节级改动）；
3. 把文件发回给你，说"这是你上次的备份，打开看看"；
4. 你输入备份密码 → 按 `iter=1` 派生 KEK → **派生结果完全相同**（因为参数是文件里写的）→ 文件正常打开，看不出任何异常。

而对方手里那份文件，暴力破解只需要 1 次迭代的成本，而不是 21 万次。加密还在，强度被抽走了。

把文件头纳入 AAD 后，改任何一个字节都会让 TAG 校验失败 → 提示「备份密码不正确，或文件已被修改」。

> 这一条被单独写成了一个测试：`改文件头里的迭代次数就打不开`。

### 为什么版本号错误和密码错误要分开报

- **容器版本不认识** → 「请升级应用后再打开」（换手机/换应用版本）
- **TAG 校验失败** → 「备份密码不正确，或文件已被修改」（再想想密码 / 重新拷文件）

两者混在一起报"打开失败"，用户根本不知道该往哪个方向修。代码里用两个异常类型区分：`BackupFormatException` 与 `BackupPasswordException`。

## §4 导入的四条规则

`VaultRepository.importSnapshot(snapshot, overwrite)` 在一个事务里做完，顺序不能换：

1. **分类先落库**。条目的 `category_id` 有外键指向 `categories`，父行不存在时插入会直接抛约束错误。所以先补分类，再过滤掉指向"仍然不存在"的分类 id（`validCatIds`），把这类条目的分类置空 —— 而不是让整条插入失败。
2. **已存在的 id**：`overwrite = false` 时跳过并计入 `skipped`；`true` 时覆盖。默认是 `false`，UI 上是一个默认关闭的开关，文案写「覆盖已存在的条目（同 id）」。
3. **自定义字段沿用备份里的 id**。字段密文的 AAD 是 `字段id|cf_value`，换 id 等于以后永远解不开。所以 `CustomFieldDraft(id = it.id, …)` 而不是 `id = null`。
4. **`hostNorm` 优先用备份原值**，只有它为空时才从 `url` 反推。原因：原生 App 捕获的条目**没有 url，只有 packageNorm**。如果导入时统一从 url 重算，这类条目会永久失去自动填充匹配能力。

### 刻意不做的三件事

| 不做 | 原因 |
|---|---|
| 不写 `entry_history` | 导入不是"用户改了密码"，写进去会让历史记录里出现一堆没人操作过的条目 |
| 不动 `site_mappings` | 站点映射是"在这台手机上用出来的"结果。导入进来的条目还没被用过，凭空建立映射会让候选排序失真 |
| 分类只增不改 | 同名分类可能是用户在本机改过名的，覆盖会把用户的命名打回去 |

## §5 审计日志

### 记什么

`EVENT_UNLOCK_OK` / `UNLOCK_FAIL` / `LOCK` / `COPY` / `REVEAL` / `CREATE` / `UPDATE` / `DELETE` / `EXPORT` / `IMPORT`。

### 绝不记什么

`detail` 字段里**永远不能出现明文凭据**。现在的取值只有 `"password"` / `"password changed"` / `"master password changed"` / `"biometric enabled"` 这类固定串。这一条写进了 `AuditLogEntity` 的类注释 —— 它是全工程唯一一个"看起来无害、但一旦写错就把密码写进数据库"的字段。

### 显示上限

库里保留 2000 条（`AUDIT_KEEP`），但界面只渲染 300 条（`MAX_SHOWN`）。一次渲染 2000 个 Card 会明显卡顿，而这 300 条足够回答"最近有没有人来过"。

`targetId` 只显示前 8 位（`#a1b2c3d4`）：截图发给别人时不该带完整 UUID。

### 清空

"清空"只删记录，**不记一条 `audit cleared`** —— 否则用户会看到"我清空了，页面上还有一条"，以为没清干净。

## §6 生物识别：为什么是两把 key

工程里现在有**两把** Keystore key，它们不是重复，职责完全不同：

| | `DeviceKeyStore`（W2 起） | `BiometricKeyStore`（本阶段） |
|---|---|---|
| 别名 | `vaultbook.device.capture.v1` | `vaultbook.biometric.v1` |
| 需要认证 | 不需要（设备锁屏保护即可） | **每次使用都要过指纹** |
| 保护什么 | 待确认捕获（临时数据，≤7 天） | DEK 的第二份包裹（正式库的钥匙） |
| 新录指纹后 | 不受影响 | **整把 key 作废** |
| 用于 | `KeystoreFieldCipher` | `AuthenticatedCipherWrapper` |

**合并成一把会怎样**：捕获通道必须在锁屏状态下就能写（否则用户登录网站那一刻如果 App 锁着就永远抓不到），给它配上"能开正式库"的钥匙，等于把主密码的安全等级降到"解锁手机即可"。

### `setInvalidatedByBiometricEnrollment(true)` 的取舍

打开它意味着：用户后来在系统里录入**新指纹**，这把 key 立刻作废，指纹解锁失效、必须回主密码。

听起来不友好，但这正是生物识别的意义 —— 别人把**自己的**指纹录进你的手机，就不该还能打开你的保险库。代价是换膜/重录指纹后需要重新启用一次，UI 上会明确提示「密钥已失效（改过锁屏密码或录了新指纹），请关闭后重新启用」。

### 为什么 `MainActivity` 要改成 `FragmentActivity`

`androidx.biometric.BiometricPrompt` 的构造参数要求 `FragmentActivity`。而 `FragmentActivity` 本身继承 `ComponentActivity`，所以：

- `setContent { }` 与整个 Compose 树照常工作；
- 生命周期回调（`App.kt` 里的 `ForegroundWatcher`）行为不变。

改动只是 `class MainActivity : ComponentActivity()` → `: FragmentActivity()`，外加显式声明 `androidx.fragment:1.8.5` 依赖（`biometric` 会传递依赖它，但传递依赖的 scope 不受我们控制）。

### 认证结果只认回调里的 cipher

```kotlin
if (result.cryptoObject?.cipher != null) onSuccess()
else onError("认证完成但未拿到可用的密钥")
```

不认我们自己创建的那个 `cipher` 实例。`CryptoObject` 的语义就是"认证通过后系统授权的那一个"，拿自己的实例继续用可能拿到一个未授权的对象（不同 ROM 表现不一致）。

### 用户取消不是错误

`ERROR_USER_CANCELED` / `ERROR_NEGATIVE_BUTTON` / `ERROR_CANCELED` 三个错误码静默返回，不弹提示。同理 `onAuthenticationFailed`（指纹不匹配）也什么都不做 —— 系统自己会显示"再试一次"，我们再弹一个横幅，会让"手指放歪"看起来像出了故障。

## §7 本阶段修掉的问题

| # | 问题 | 处理 |
|---|---|---|
| 1 | `AuditLogScreen` / `BackupScreen` 三处在协程闭包里直接用了可空的 `repo`，编译报 "Only safe calls are allowed on a nullable receiver" | 闭包里局部取一次非空别名（`val r = repo ?: return@launch`），而不是加 `!!` —— 后者会把"理论上不可能"变成崩溃 |
| 2 | `BackupFormat.unpack` 曾把长度检查从"至少"错写成"精确相等" | 只在测试里发现：所有正常文件都被拒（密文长度 = 明文长度 + TAG，不固定）。已改回下限检查，并在注释里记下这个坑 |
| 3 | 「版本过高」的提示文案只有"不受支持"，用户不知道该干什么 | 补成「请升级应用后再打开」 |
| 4 | 备份测试里「尾部多余字节应失败」这条断言本身是错的 | `unpack` 只做结构下限校验，尾部追加由 GCM TAG 负责。改成两条更准确的测试：结构不成立（`unpack` 拒收）与截断一字节（`open` 失败） |

## §8 真机验证

### 备份（8 步）

1. 列表页 → 右上角 ⋮ → 设置 → 导出加密备份。
2. 输入备份密码（≥8 位，**不要**和主密码相同）。
3. 系统保存对话框 → 存到「下载」或共享给网盘。
4. 用文件管理器确认生成了 `vaultbook-backup-YYYYMMDD-HHmm.vbc`，大小几 KB 到几十 KB。
5. 回到应用 → 设置 → 导入备份 → 选刚导出的文件。
6. 应先看到「文件头正常：PBKDF2-HMAC-SHA256，210000 次迭代 / 共 N 条」，再让你输密码。
7. 输**错误**密码 → 提示「备份密码不正确，或文件已被修改」。
8. 输正确密码 → 显示「新增 0 条，覆盖 0 条，跳过 N 条」—— 因为都是同一批数据、id 相同。

> 想真正验证"能恢复"，只能在另一台设备上导入，或者导出后把应用数据清掉再导入。**清数据前务必确认备份文件已经拷出手机。**

### 指纹（5 步）

1. 解锁后进设置 → 打开「指纹解锁」→ 系统弹指纹框 → 验证通过。
2. 锁定（列表页右上角锁图标）→ 解锁页应多出「用指纹解锁」。
3. 点它 → 验证 → 自动进入列表页。
4. 去系统设置里**录入一根新指纹** → 回解锁页点指纹 → 应提示「指纹密钥已失效…请用主密码解锁后在设置里重新启用」。
5. 回设置页，开关显示为关闭（`KEY_INVALIDATED` 状态）→ 关闭再打开即可恢复。

### 审计（2 步）

1. 设置 → 审计日志：应能看到刚才的解锁、复制密码、导出、导入记录。
2. 点清空 → 确认 → 列表变空（不会留下一条"已清空"）。

## §9 已知限制

| 限制 | 说明 |
|---|---|
| 备份文件的 `hostNorm`/`packageNorm` 是明文 | 与数据库里的取舍一致：自动填充需要毫秒级按站点查。备份文件被看到，只暴露"注册过哪些站点" |
| 导入不做跨库冲突解决 | 只按 `id` 判重。两台手机各自新建的条目 id 不同，导入后会出现两条同站点记录 —— 这是刻意的（无法判断哪条"更新"更可信） |
| 指纹只支持强生物识别 | 屏下指纹/面容通常满足；某些只支持 2D 人脸的设备会显示"不支持"，此时只能主密码 |
| 备份密码没有强度下限强制 | 只提示不拦截（`MIN_BACKUP_PASSWORD = 8`）。用户的备份策略不该被应用硬卡 |
| 备份文件不带完整性校验之外的元信息 | 没有"导出时的应用版本""导出设备"字段 —— 少一个字段少一处兼容负担 |

⚠️ **仍未在真机上运行过。** 本阶段新增的两块能力都有"只有真机能回答"的部分：

1. **指纹**：`BiometricPrompt` 的行为在不同 ROM 上差异很大（有的会在认证成功后返回 null 的 `cryptoObject`，有的把"取消"映射成别的错误码）。如果指纹一直提示失败，先看 `docs/07 §7` 的排查思路。
2. **文件选择器**：`ActivityResultContracts.CreateDocument` / `OpenDocument` 在部分国产 ROM 上的实现是自家文件管理器，可能不返回 `content://` 而是别的 scheme。若导入时提示"文件头异常"，多半是打开失败而不是格式问题。
3. **R8 后的反射**：`BiometricPrompt` 与 `RemoteViews` 都用了反射，已经通过 `assembleRelease` 但没有在真机跑过 `release` 包。
