## 2. 数据层结构

```
UI (Compose)
   │  只用 EntrySummary / EntryDetail / EntryDraft（全是明文或 CharArray）
   ▼
VaultRepository           ← 唯一知道"哪个字段是密文、AAD 用什么"的地方
   │  FieldCipher（AES-256-GCM，密钥来自已解锁的 DEK）
   ▼
DAO (Room)                ← 只认 ByteArray，不认识业务含义
   ▼
VaultDatabase             ← SQLCipher（AES-256，整库加密）
   ▲
   │ dbKey
VaultGateway              ← 密钥 → 开库 → 建仓储；锁定 → 关库 → 销毁密钥
   ▲
   │ VaultKeys { dek, dbKey }
KeyManager / VaultSession ← W0 已交付
```

两层加密各管一段，互不替代：

| 层 | 算法 | 挡什么 |
|---|---|---|
| SQLCipher 整库 | AES-256-CBC + HMAC | 拿到 `vault.db` 文件也打不开 |
| 字段级 | AES-256-GCM，AAD=`entryId\|fieldName` | 库被打开后，把 A 条目的密码密文挪到 B 条目会被识破 |

## 3. 与 `docs/02` 设计的三处偏差（都是有意的）

### 3.1 `vault_meta` 改存 SharedPreferences，不建表

**原因**：先有鸡还是先有蛋。开 SQLCipher 需要 `dbKey`，而 `dbKey` 就在 `vault_meta` 里。

**这样做安全吗**：安全。那个文件里没有任何明文密钥——`DEK` 被 `KEK` 包着、
`dbKey` 被 `DEK` 包着、校验串被 `DEK` 加密过。攻击者拿到文件，没有主密码也解不开任何一层。

**为什么用 `commit()` 不用 `apply()`**：改主密码时要保证"新元数据落盘"与"旧密码失效"是原子的。
`apply()` 是异步的，进程在这中间被杀会留下半状态——旧的解不开、新的没写完，等于丢库。

### 3.2 `entries` 上的索引退化为普通索引

`docs/02` 的 DDL 写了部分索引 `WHERE deleted_at IS NULL`，但 **Room 不支持部分索引**。
退化为普通索引的代价只是回收站里的条目也被索引到，查询侧一律带 `deleted_at IS NULL`，
结果集不受影响。

### 3.3 搜索不用 SQL `LIKE`

字段全是密文，`LIKE` 无从下手。做法是：解锁后把 `title / username / url / host_norm`
解密到内存，列表页预计算一份归一化索引，输入时只做 `contains`。
1000 条量级下每次按键 < 5ms。**密码字段不参与搜索、不预加载。**

## 4. 加密落地点：AAD 字段名

这些字符串是 `AAD = entryId | fieldName` 的一半。**改一个字符，旧数据就全部解不开。**

| 常量 | 值 | 用在哪 |
|---|---|---|
| `FIELD_TITLE` | `title` | 条目标题 |
| `FIELD_USERNAME` | `username` | 账号 |
| `FIELD_PASSWORD` | `password` | 密码 |
| `FIELD_URL` | `url` | 网址 |
| `FIELD_NOTES` | `notes` | 备注 |
| `FIELD_TOTP` | `totp` | TOTP 种子 |
| `FIELD_CATEGORY_NAME` | `name` | 分类名（AAD 用分类 id） |
| `FIELD_CF_LABEL` | `cf_label` | 自定义字段标签（AAD 用字段 id） |
| `FIELD_CF_VALUE` | `cf_value` | 自定义字段值（AAD 用字段 id） |

自定义字段的 `id` 因此必须**跨次编辑保持稳定**——每次保存都换新 id 的话，旧密文就再也解不开了。

## 5. 两个关键写路径

### 5.1 新建条目

```
EntryDraft(title, username, password: CharArray?, url, ...)
  → 生成 UUID
  → 每个字段 cipher.encrypt(entryId, fieldName, …)     逐字段随机 IV
  → hostNorm = Normalize.hostFromUrl(url)
  → strengthScore = PasswordStrength.score(password)
  → 事务：upsert(entries) + 写 custom_fields + 写 audit_log
```

### 5.2 修改密码（顺序不能错）

```
if (新密码非空) {
    entry_history.insert(旧密文)     ← 必须先做
    entry_history.trim(keep = 20)    ← 超 20 条删最老的
}
entries.upsert(新密文)
```

**为什么必须先写历史再更新主表**：反过来的话，`upsert` 一提交旧密文就没了，
"改错密码想回滚"这条路彻底断掉。

## 6. 怎么验证

### 6.1 真机手动验证（5 分钟）

1. 安装 → 打开 → 设主密码（≥8 位）→ 记牢
2. 右下角 `+` → 填标题 `测试` / 账号 `a@b.com` / 点「生成」拿到 20 位密码 → 保存
3. 列表里出现「测试」和 `a@b.com`，左侧色点显示强度
4. 点进去 → 密码框是空的、提示「留空表示不修改」→ 点「查看当前密码」能看到刚生成的密码
5. 点「复制」→ 粘到别处是那串密码 → **等 30 秒**再粘，剪贴板应已清空
6. 改一下标题 → 保存 → 列表标题变了，密码还能查看（说明 `password == null` 时保留了原密文）
7. 按 Home 键 → 等 35 秒 → 回到 App：**应该已经在解锁页**
8. 输错主密码 → 提示"主密码不正确"，不是"数据损坏"

第 7 步是 W1 最值得测的：它同时验证了前后台计数、`elapsedRealtime` 时钟、
`gateway.lock()` 的关库顺序三件事。

### 6.2 单元测试

```bash
./gradlew :app:testDebugUnitTest
```

应全绿 118 项。若 `gradlew` 不存在，先在 Android Studio 里 Sync 一次。

### 6.3 确认数据库真的加密了

真机或模拟器上：

```bash
adb shell run-as com.yg.vaultbook.debug ls -l databases/
adb shell run-as com.yg.vaultbook.debug head -c 16 databases/vault.db | xxd
```

第 16 字节起应是随机噪声，而不是 `CREATE TABLE` 之类的明文 SQL。
**如果能看到 `SQLite format 3` 后的可读表结构，说明 SQLCipher 没生效。**

## 8. 这一周踩到的坑（都写进代码注释了）

| 坑 | 后果 | 现在怎么做 |
|---|---|---|
| `@Insert(onConflict = REPLACE)` 更新条目 | REPLACE 实际是 DELETE+INSERT，`entry_history` / `custom_fields` 带 `ON DELETE CASCADE`，**更新一条记录会顺手删掉它的密码历史和自定义字段** | 一律 `@Upsert` |
| 自动锁定用 `System.nanoTime()` | 深睡时 `nanoTime` 不走，"锁屏放一晚"的间隔算成 0，自动锁定永不触发 | `SystemClock.elapsedRealtime()` |
| 元数据用 `apply()` 落盘 | 改主密码时进程被杀会留下半状态：旧密码失效、新密码没写完 | `commit()` |
| `lock()` 先销毁密钥再关库 | `close()` 期间 SQLCipher 还要用口令做页写入，可能拿到清零的密钥 → 元数据页损坏 | **先 `close()` 再 `lock()`** |
| `@Query` 的 Flow 里写了 `expires_at > :now` | Flow 长期订阅，`now` 在订阅时就固定了，越往后越返回过期数据 | Flow 不带时间条件，过期过滤在仓储层用注入时钟做 |
| `String.ifBlank { null }` | `ifBlank` 的返回类型必须是 `CharSequence` 的子类型，`null` 编译不过 | `?.trim()?.takeIf { it.isNotEmpty() }` |
| 主密码框用 `rememberSaveable` | 内容会进 `savedInstanceState`，被系统序列化到磁盘 | `remember`，代价是旋转屏幕清空输入 |
