# v1.7.3 第二批优化说明

> 对应版本：`versionCode 13` / `versionName 1.7.3`（2026-10-31）
> 上一批见 [docs/21-v1.7.2优化说明.md](21-v1.7.2优化说明.md)

## 1 这一批在修什么

上一批修的是「已经错、只是还没被踩到」的地方（筛选条说谎、剪贴板清理随进程死、重建丢页面、两条空转权限、32 位 ABI 白占体积）。

这一批全部是「没错，但做得笨」的地方：

- 一件只需要算一次的活儿，每次列表变动都在**主线程**重算一遍；
- 查询把每行最重的两列（笔记、密码密文）也搬出 SQLite，只为了判断它「有没有」；
- 桌面小组件在列表每次变动时都重写一遍缓存并广播一次；
- Android 15 起系统强制 edge-to-edge，之前只有部分页面处理了安全区；
- 离开列表页再回来，滚动位置、搜索词、筛选条、入场动画状态全丢。

没有一条是用户会「看见」的改动。收益要等条目上千，或者手机换成 Android 15 才显形。

## 2 逐条改法

### 2.1 搜索索引与计数：一次遍历，挪到后台

改动前，`EntryListScreen` 在组合期跑两段 `remember(items)`：

```kotlin
val searchIndex = remember(items) { items.associate { it.id to Pinyin.searchKey(it.searchText()) } }
val counts = remember(items) { QuickCounts(all = items.size, favorite = ..., byCategory = ...) }
```

`searchText()` 要把标题、账号、网址、归一化域名四个字段拼起来，再走一遍全角转半角、大小写归一、拼音首字母转换 —— **每条一次，全表一次**；紧接着再全表数一遍收藏数和分类计数。条目到一千条时，第一次进列表有可感知的停顿，而且每次增删改都重来一次。

改成：

```kotlin
val derived by produceState(ListDerived.EMPTY, items) {
    value = if (items.isEmpty()) ListDerived.EMPTY
            else withContext(Dispatchers.Default) { computeListDerived(items) }
}
```

`computeListDerived()` 单次遍历同时产出搜索索引 `Map` 与 `QuickCounts`，全程在 `Dispatchers.Default` 上。

为什么用 `produceState` 而不是自己起协程：它把「派生值 + 异步计算 + 取消」绑在一起，`items` 再变时旧协程自动取消，不需要手写 `Job` 管理，也不会出现两个计算结果互相覆盖。`ListDerived.EMPTY` 作为初始值是必要的 —— `filtered` 依赖 `derived`，异步计算期间拿到的应当是一个空的、结构完好的对象，而不是 `null`。

### 2.2 列表查询改投影：密文一个字节都不出库

`EntryDao.observeActive()` 原来是 `SELECT *`。`EntryEntity` 里最重的两列是 `notes_ct`（备注密文）和 `password_ct`（密码密文）—— 长度随内容增长，一千条时是 MB 级的搬运，而列表页一个字符都用不上它们，只用得上「有没有」。

新增 `EntrySummaryRow`（`data/entity/EntryEntities.kt`）与两条查询（`data/dao/EntryDao.kt`）：

```sql
SELECT id, category_id, title_ct, username_ct, url_ct, host_norm, package_norm,
       favorite, strength_score, pwd_updated_at, created_at, updated_at,
       last_used_at, use_count, deleted_at,
       (password_ct IS NOT NULL) AS has_password,
       (totp_ct IS NOT NULL) AS has_totp
FROM entries
WHERE deleted_at IS NULL
ORDER BY favorite DESC, COALESCE(last_used_at, 0) DESC, updated_at DESC
```

关键点是两个布尔：`has_password` / `has_totp` 在 SQL 里就算完了，Kotlin 侧不需要解密也不需要判空逻辑。

要点：

- **不是 schema 变更**：没有新表、没有新列、`VaultDatabase` 版本没动，老库直接打开，不需要迁移；
- 排序条件与原 `observeActive()` 逐字一致，列表顺序不变；
- 原 `toSummary(e: EntryEntity)` 保留 —— `summaryOf(id)` 与 `loadDetail(id)` 仍走实体路径。

### 2.3 小组件刷新加 400 ms 去抖

原来 `LaunchedEffect(items)` 里每次列表变动都 `WidgetCache.save(...)` + `VaultWidgetProvider.refresh(context)`。连续编辑、连续删除时，一次保存操作会触发好几轮广播；而系统对 AppWidget 更新本身有频率限制，撞上去就是「更新被丢掉」，表现为小组件停在旧内容。

改成在写缓存之后先 `delay(WIDGET_REFRESH_DEBOUNCE_MS)`（400 ms）。`LaunchedEffect` 的键一变就取消上一个协程 —— 天然实现「只跑最后一次」，不需要额外的定时器或时间戳比较。

`cachePrimed` 守卫保留：首帧 `items` 还是空列表时不能把空内容写进小组件。

### 2.4 Android 15 的 edge-to-edge

`targetSdk 35` 在 Android 15 上系统强制 edge-to-edge，且不允许应用 opt-out。之前布局在 API 26~34 上靠系统给的栏底色蒙过去，到 15 上会变成内容顶到状态栏。

先做了一次审计，结论是所有页面都已经用 `Scaffold` 且都消费了 `innerPadding`，而 `Scaffold` 默认的 `contentWindowInsets` 已包含系统栏 —— 所以只需要在 `MainActivity.onCreate` 里显式 `enableEdgeToEdge()`，让 26~34 与 15 走同一套布局。

两处手工 inset 是正确的、不是重复边距，已确认保留：

| 位置 | 原因 |
|---|---|
| `EntryListScreen.kt` 的 `ListHeader.statusBarsPadding()` | `ListHeader` 放在 `Scaffold` 的 `topBar` 槽，M3 **不会**替 `topBar` 加状态栏 inset |
| `EntryDetailScreen.kt:243` 的 `navigationBarsPadding()` | 底部操作条不在 `Scaffold` 的 `bottomBar` 槽内 |

### 2.5 页面状态槽：离开再回来，原位恢复

改动前只有「当前是哪个页面」进了 `rememberSaveable`，页面内部状态（搜索词、筛选条、滚动位置、已播过的入场动画）随组合销毁一起消失。表现是：进详情、返回，列表回到顶部；在列表搜了个词、去设置、回来，搜索框空了。

`VaultApp.kt` 里加 `rememberSaveableStateHolder()`，按 `Screen.key()` 分槽：

```kotlin
private fun Screen.key(): String = when (this) {
    Screen.List -> "list"
    Screen.Pending -> "pending"
    Screen.Trash -> "trash"
    Screen.Generator -> "generator"
    Screen.Categories -> "categories"
    Screen.Settings -> "settings"
    Screen.Backup -> "backup"
    Screen.Audit -> "audit"
    is Screen.Detail -> "detail:$entryId"
    is Screen.Edit -> "edit:${entryId ?: "new"}"
}
```

`AnimatedContent` 的 content 里用 `saveableStates.SaveableStateProvider(page.key()) { ... }` 包住 `when (page)`。

这样不用引入 Navigation-Compose：它的 `saveState` / `restoreState` 本质就是这套机制，树浅的项目自己拿 holder 更直接，也少一个依赖。

两处状态另外单独提到 `VaultApp`：

- **列表滚动位置**：`rememberSaveable(saver = LazyListState.Saver) { LazyListState() }`。滚动位置属于「用户的位置感」，切走再回来必须原位，不能靠组合重建。
- **入场动画的 `playedIds`**：普通 `remember { mutableSetOf() }`，故意不跨进程保存 —— 动画重播一次不算问题，而为了它序列化整个 Set 不划算。

### 2.6 关于「删 VaultGateway 死代码」——决定不删

原计划删掉 `VaultGateway` 里约 120 行主密码 API（`createVault` / `unlock` / `changeMasterPassword` / `hasVault` / `lock`），理由是 UI 层零调用。

核对后放弃，原因有两条：

1. `KeyManager` 是 `CryptoSelfTest.kt`（加密自检页）、`KeyManagerTest`、`VaultSessionTest` 的直接依赖，这些测试大量调用 `createVault` / `changeMasterPassword` / `unlock` / `lock`。删掉 Gateway 这层包装只是把调用挪到别处，测试基础设施照样要留，代码量并不减少。
2. R8 在 release 构建里本来就会剥掉无引用方法，这个方法对 APK 体积的贡献是 0 字节。

结论：留着。它现在的角色是「加密层自检的入口」，删了反而要改三套测试。

## 3 结果

| 项 | 改前 | 改后 |
|---|---|---|
| 列表派生计算 | 组合期主线程，两次全表遍历 | 后台单次遍历，异步可取消 |
| 列表查询宽度 | `SELECT *`（含备注、密码密文） | 投影，密文不出库 |
| 小组件刷新 | 每次列表变动都写缓存 + 广播 | 静默 400 ms 后一次 |
| Android 15 | 内容可能顶到状态栏 | 主动 edge-to-edge，全版本一致 |
| 离开页面再回来 | 搜索词 / 筛选 / 滚动 / 动画全丢 | 原位恢复 |
| APK 体积 | 7.03 MB | 7.03 MB（这批不涉及体积） |
| 单元测试 | 23 类 / 374 项全绿 | 23 类 / 374 项全绿 |

## 4 还没做的（第三批）

| 内容 | 为什么值得做 | 为什么还没做 |
|---|---|---|
| **CSV 导入** | 换机时手里大多是一张表格（微信收藏、Excel、旧手机导出），这是唯一真正拦人的门槛 | 要定格式（列名映射、分隔符、编码、冲突策略），是交互设计题不是编码题 |
| **备份提醒** | 明文落在本机、又没有云同步，丢手机就全丢；用户不会自己想起来导出 | 需要在 prefs 记 `lastBackupAt`，并在列表页做一次性提示，牵扯到「多久算久」的产品判断 |
| **本地安全体检** | 重复密码 / 弱口令 / 长期未用 / 未存 TOTP，全离线可算，对用户是实打实的价值 | 需要一个新的结果页与筛选联动，工作量在 UI 不在算法 |
| 多语言 | — | 文案上千条硬编码在 Composable 里，抽取成本远大于收益 |
| 云同步 | — | 与「不联网」的产品定位直接矛盾 |

## 5 验收方式

```powershell
adb install -r dist\账号本-1.7.3.apk
```

改动都是行为等价或纯收益型，验收看三点：

1. 列表页滚动到中段 → 进任意条目详情 → 返回，应停在原位（不是回到顶部）；
2. 列表页输入搜索词 → 进设置 → 返回，搜索框与筛选条应保留；
3. 桌面小组件在批量删除几条后，应在半秒内跟上（而不是要手动刷新）。
