## 2. 核心问题：锁着的时候也得能抓

这是 W2 唯一真正难的地方。

> 用户在浏览器里点「登录」的那一刻，本 App 处于**锁定**状态
> —— 自动锁定是 30 秒，而打开浏览器、找站点、输账号通常要一分钟以上。

如果"捕获"这件事要求先解锁，那这个功能在最常见的场景下就是失效的。
但锁定时没有 DEK，写不进 `pending_captures`（那张表在 SQLCipher 里，开门要 dbKey，dbKey 要主密码）。

### 三条路，选了第三条

| 方案 | 后果 |
|---|---|
| 锁定时不存 | 核心功能失效 —— 恰好是最常见的场景 |
| 用设备密钥包裹 dbKey，锁定时也开主库 | 攻破设备锁屏 = 攻破整个库，主密码的保护语义没了 |
| **独立小文件 + 字段级设备密钥加密** | 只有"待确认"这一小块受设备密钥保护，主库钥匙始终只由主密码解封 |

### 数据流

```
锁定状态
  浏览器提交登录
    └─ onFillRequest 已返回「只带 SaveInfo」的响应
         └─ onSaveRequest 被系统回调
              └─ KeystoreCaptureQueue.enqueue()   ← 设备密钥加密三个字段
                   存 filesDir/pending_captures.json（≤20 条，≤7 天）

用户解锁
  └─ VaultGateway.openInternal()
       └─ drainCaptureQueue()
            └─ CaptureRepository.importRows()   ← 密文原样搬进表（AAD 口径一致）
                 └─ 文件删除
```

**代价写明白**：这个文件里的密文在设备解锁状态下不必输主密码就能读。
所以它只装待确认数据、只留 7 天、解锁即搬走。
`entries` 里的正式凭据永远只由主密码解封的 DEK 加密，设备密钥碰不到。

## 3. 最关键的一条：SaveInfo 必须无条件给

`onSaveRequest` **只在本 service 于本次 `onFillRequest` 里返回过含 `SaveInfo` 的响应时才会被回调。**

也就是说，"锁定时为了安全什么都不返回"的真实后果是：

> 用户手动输入的密码**永远抓不到**，整个自动捕获功能形同虚设。

所以 `VaultAutofillService.onFillRequest` 的流程被固化成这样：

```
解析 AssistStructure
  ├─ 没有密码框              → finish(null)      （没什么可存的）
  ├─ 有密码框但凑不出 SaveInfo → finish(null)      （此时任何 FillResponse 都构造不出来）
  ├─ 保险库锁定              → finish(只含 SaveInfo 的响应)   ← 关键
  └─ 保险库已解锁            → finish(候选 + SaveInfo)
```

`AutofillResponseBuilder` 的类注释里把这条列为三条硬约束的第 2 条，
因为它一改就静默失效，测试也发现不了（要真机重装系统才复现）。

## 4. 打分：为什么"宁可少推荐"

### 4.1 候选排序（`SiteMatcher`）

基础分**取最高一项，不叠加**：

| 依据 | 分 | 说明 |
|---|---:|---|
| 有站点映射记录 | 100 | 用户之前在这个站点选过这一条，最可信 |
| 域名完全一致 | 80 | `host_norm == 当前域名` |
| 包名完全一致 | 70 | 原生 App |
| 域名后缀一致 | 45 | `new.taobao.com` 命中 `taobao.com` 的条目 |

加分：账号与页面已填内容一致 +25、收藏 +6、最近 30 天用过 +10（线性衰减）。
减分：**没有密码 −40**（没有密码的条目填上去等于没填）。

门槛 `MIN_SCORE = 30`，最多 5 条。

> 有个反直觉的结果，已在单测里固定下来：
> `域名完全一致但账号不符`（80）> `域名后缀一致且账号相符`（45+25=70）。
> 网址匹配是比"页面已填账号"更硬的证据，因为用户完全可能在同一台手机的浏览器里
> 登录过别人的账号。

### 4.2 账号匹配不做模糊

`sameUsername` 只做「去空白 + 小写」比较。
`alice` 与 `alice2`、`alice` 与 `alice@2` 都**不匹配**。

理由：猜错会把 A 账号的密码填进 B 账号的输入框，用户点一下就用错了账号登录，
还不一定立刻发现。宁可少给一个加分。

### 4.3 捕获置信度（`CaptureConfidence`）

| 证据 | 权重 |
|---|---:|
| 有密码框 | 0.35 |
| 有账号框 | 0.25 |
| 认出站点/包名 | 0.20 |
| 检测到提交 | 0.10 |
| 页面标题非空 | 0.10 |

- `≥ 0.85` → **高可信**（待确认列表里标"高可信"）
- `0.60 ~ 0.85` → **待确认**
- `< 0.60` → **丢弃**

分数收敛到两位小数。不收敛的话浮点累加会得到 `0.60000004`，阈值判断在边界上随机翻转。

> 已知取舍：只有密码框、站点又认不出来的页面（0.35）会被丢弃。
> 银行常见的"先输卡号，下一页才输密码"就是这种形态。
> 漏存一条用户还能手动补，错存一条会污染匹配学习结果 —— 而错误数据比没有数据更难纠正。

## 5. 字段识别：几个真实会踩的坑

`AutofillHints.classify` 的优先级（从硬到软）：

```
不可编辑 → IGNORE
排除关键词（search/captcha/code/验证码/搜索…）→ IGNORE
  ↳ 例外：htmlType == "password" 或密码型 inputType 时压过排除项
autofillHints 含 password/newPassword/currentPassword → PASSWORD
autofillHints 含 username/emailAddress/phone…        → USERNAME
htmlType == "password" / "email" / "tel"
密码型 inputType
关键词兜底（密码优先于用户名）
→ UNKNOWN
```

| 坑 | 处理 |
|---|---|
| `AUTOFILL_HINT_NAME` 的值是 `"name"`，指的是**真实姓名** | `HINT_USERNAME` 里故意不含 `"name"`。否则收货地址表单的姓名框会被当成账号框，把姓名填进登录框 |
| `password` 含 `word`，`username` 含 `name` | 关键词表里不能有 `word` / `name` 这类泛词，否则用户名框会被判成密码框，密码以明文填进可见框 |
| `0x10` 这个 variation：TEXT 类下是 URI，NUMBER 类下才是密码 | `isPasswordInputType` 先看 `MASK_CLASS` 再看 variation，两者同时匹配才算 |
| `userpassword` 同时命中密码和用户名关键词 | 密码优先。判错的代价不对称：填反了密码会明文暴露 |
| 搜索框 id 常是 `q` / `keyword` / placeholder「搜索」 | 显式排除，否则用户一点搜索框就弹"填充账号密码" |
| 已经输入的 `value` 会污染判断 | `buildHaystack` 只取 `id`/`name`/`placeholder`/`aria-label`/`title`/`autocomplete`，**不取 value** |

## 6. 两个顺序问题（写错就静默失效）

### 6.1 `onSaveRequest`：先落盘，再 `onSuccess`

```kotlin
val queued = gateway.captureQueue.enqueue(input)   // 先写文件
input.clearSecrets()
callback.onSuccess()                                // 再告诉系统
```

反过来（先 `onSuccess` 再写）的话，系统可能在写文件之前就把本进程回收掉，
这条捕获**永久消失**，而且没有任何报错。

### 6.2 `VaultGateway.lock()`：先关库，再销毁密钥

```kotlin
fun lock() {
    closeCurrent()   // SQLCipher close，可能还要用口令做最后的页写入
    session.lock()   // 销毁并清零密钥
}
```

先销毁密钥的话，`close()` 期间拿到的是已清零的数组 ——
轻则抛异常，重则留下一个元数据页损坏的库文件。

## 7. 验证方法（真机 10 分钟）

准备：一台 API 26+ 的手机，装上 debug 包。

1. **建库**：设主密码（≥8 位）→ 建一条手动记录（标题「测试站」，账号 `me@test.com`，密码点「生成」）。
2. **开服务**：设置 → 系统 → 语言和输入法 → 自动填充服务 → 选「账号本」。
3. **填一次**：用系统浏览器打开任意登录页（例如 `https://passport.bilibili.com/login`），
   点账号框 → 应该弹出「账号本」的候选。**若弹出候选但点了没反应，是 `autofill_dataset.xml` 的控件不被 RemoteViews 支持。**
4. **抓一次（关键）**：在登录页**手动输入**一个从没存过的账号密码并提交。
   回到账号本 → 右上角铃铛应出现角标。
5. **验证锁定路径**：按 Home 键等 35 秒（自动锁定）→ 再在浏览器登录另一个站点 →
   回到账号本解锁 → **那条捕获应该已经在待确认列表里**。
   这是 W2 最重要的一条，它验证的是 `KeystoreCaptureQueue` 整条链路。
6. **保存**：点「保存」→ 回列表应看到新条目，且「待确认」计数归零。
7. **再填一次**：回到那个网站 → 这次候选里应该出现刚保存的条目。
8. **验证映射**：保存过的站点第二次填充时，该条目应排在最前面（mapping 加分）。

排查：

| 现象 | 可能原因 |
|---|---|
| 第 3 步没候选 | 服务没选中 / 页面是 Flutter 自绘（无 autofillId） |
| 第 4 步没角标 | `onFillRequest` 没返回 SaveInfo，或 `onSaveRequest` 崩了（看 logcat `VaultAutofill`） |
| 第 5 步丢捕获 | 自动锁定没生效（检查 `App.kt` 是否用的 `elapsedRealtime`） |
| 第 5 步丢捕获但锁屏后重开才有 | 正常：`onTrimMemory` 会锁，但 drain 要等下次解锁 |
| 第 6 步「保存失败」 | 设备密钥被作废（改过锁屏密码），待确认记录读不出来 |

## 8. 已知缺失

| 缺什么 | 影响 | 计划 |
|---|---|---|
| 无障碍通道（`CaptureAccessibilityService` 仍是空实现） | Flutter/RN 自绘登录页完全抓不到 | W3 |
| 捕获后没有"立即确认"的通知/提示条 | 用户要自己发现右上角的角标 | W3 |
| 同站点多账号时，候选顺序靠账号匹配加分，不能手动指定 | 有两个账号时常要自己挑 | W3（条目上「设为该站点默认」） |
| 注册/改密页（≥2 个密码框）也会进待确认 | 可能存进一个刚生成的临时密码 | W3（`passwordFieldCount >= 2` 降级处理） |
| 生物识别解锁、Keystore 绑定 DEK | 每次都要打主密码 | W4 |
| `KeystoreCaptureQueue` 里的密文在设备解锁时可直接读 | 见 §2 的代价说明 | 设计如此，不修 |
