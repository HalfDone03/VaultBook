# 16 · 分享进入与手动粘贴

> 版本：v1.3.1　　对应改动：4 个文件　　测试：350 项（未新增，本轮改的是 UI 接线）

---

## 1. 这次补的是两个「入口」

v1.3.0 已经能做到「复制一段文字 → 切回账号本 → 点新建 → 点从剪贴板粘贴」。
本轮把这条路修成两条更短的，理由都不是"更好看"，而是**原路有失效的可能**。

| 入口 | 解决什么问题 | 用户动作 |
|---|---|---|
| 手动粘贴对话框 | 系统禁止应用读剪贴板时，「从剪贴板粘贴」按钮点了只会说"剪贴板是空的" | 新建 → 手动粘贴 → 长按输入框粘贴 → 识别 |
| 外部分享 `ACTION_SEND` | 复制-切应用-点新建-点粘贴，四步太长 | 在任意应用选中文字 → 分享 → 账号本 |

两个入口共用同一套识别逻辑（`CredentialParser`），不存在"分享能认、粘贴认不出"的情况。

---

## 2. 为什么必须有「手动粘贴」

Android 从 10 开始限制后台应用读剪贴板。前台应用通常仍可读，但**部分国产 ROM 更严格**，
会在某些场景直接让 `getPrimaryClip()` 返回 null。

这不是"少数派问题"——恰恰在**最需要粘贴识别**的时刻（刚从浏览器/银行 App 切过来，
我们的应用刚回到前台）概率最高。

`EntryEditScreen` 的处理：

```kotlin
fun readClipboard(): String? =
    runCatching {
        val cm = context.getSystemService(Context.CLIPBOARD_SERVICE) as? ClipboardManager
        cm?.primaryClip?.takeIf { it.itemCount > 0 }
            ?.getItemAt(0)?.coerceToText(context)?.toString()?.takeIf { it.isNotBlank() }
    }.getOrNull()
```

读不到时不再只说"剪贴板是空的"，而是明确告诉用户**还有别的路**：

```
剪贴板是空的（部分系统禁止应用读剪贴板，可用「手动粘贴」）
```

手动粘贴对话框里的输入框是普通 `OutlinedTextField`。用户在里面长按，
调起的是**系统自己的粘贴菜单** —— 那个菜单由系统进程实现，任何 ROM 都不会拦。
这条路是兜底，必须一直留着。

**没有做成"自动弹出手动粘贴框"**：读不到剪贴板时自动弹窗，会让每次正常打开新建页
都多一次干扰，而多数情况下读剪贴板是成功的。所以只在用户点了按钮之后才出现。

## 3. 为什么加 `ACTION_SEND`

注册在 `AndroidManifest.xml` 的 `MainActivity` 上：

```xml
<intent-filter>
    <action android:name="android.intent.action.SEND" />
    <category android:name="android.intent.category.DEFAULT" />
    <data android:mimeType="text/plain" />
</intent-filter>
```

**为什么限 `text/plain` 而不是 `*/*`**：分享菜单是按 mimeType 过滤的。
用 `*/*` 的话，用户分享一张照片、一个 APK 时也会看到「账号本」，
点进去得到的是一个空新建页 —— 纯粹的误点入口。文字以外的类型一律不接。

流程：

```
别的 App 分享文字
      ↓
MainActivity.handleIntent() 读 EXTRA_TEXT
      ↓
VaultApp(sharedText = ...) 检测到非空 → screen = Screen.Edit(null)
      ↓
EntryEditScreen 解析并 applyParsed()（认不出则提示，仍留空页给用户手填）
      ↓
onSharedTextConsumed() → sharedText = null
```

**分享进来的文本是直接填入、不是给"提示卡"** —— 与剪贴板的行为**故意不同**：

- 剪贴板：可能存着与本次无关的内容（上一次复制的地址、验证码），所以只给提示卡让用户点「填入」；
- 分享：用户主动在菜单里选了「账号本」，意图就是"把这段存下来"，所以直接填。

## 4. 一个必须处理的坑：Intent 会被复用

`Activity` 从最近任务恢复时，系统复用的是**同一个 Intent 对象**。
如果不清理，会出现这些现象：

- 点通知进了待确认页 → 按返回 → 切到后台 → 再切回来 → **又跳回待确认页**；
- 分享一段文字 → 保存 → 回列表 → 切到后台 → 再切回来 → **又开一个填好的新建页**。

两处都要清：

```kotlin
if (intent.getBooleanExtra(CaptureNotifier.EXTRA_OPEN_PENDING, false)) {
    openPendingSignal++
    intent.removeExtra(CaptureNotifier.EXTRA_OPEN_PENDING)
}

if (intent.action == Intent.ACTION_SEND) {
    val text = intent.getStringExtra(Intent.EXTRA_TEXT)
    if (!text.isNullOrBlank()) {
        sharedText = text
        intent.removeExtra(Intent.EXTRA_TEXT)
        intent.action = null      // 关键：连 action 一起清掉
    }
}
```

`intent.action = null` 是必须的。只 `removeExtra` 的话，`action` 仍是 `ACTION_SEND`，
下次恢复时 `getStringExtra` 返回 null（已经删了），逻辑上不再触发 ——
但如果哪天有人往这里加了"没有 EXTRA_TEXT 也做点什么"的分支，就会复发。
把 action 一起清掉更省心。

`onSharedTextConsumed` 是第二道防线：即使 Intent 清理漏了，Compose 侧消费完就置 null，
不会用同一段文本反复填。

## 5. 三条入口共用的识别函数

```kotlin
fun parseAndApply(raw: String?): Boolean {
    val parsed = CredentialParser.parse(raw) ?: return false
    if (!parsed.hasCredential) return false
    applyParsed(parsed)
    return true
}
```

返回 `Boolean` 而不是自己改 `error`，因为三条路的提示文案不同：

| 入口 | 失败时说什么 |
|---|---|
| 剪贴板 | 没从剪贴板里认出账号或密码 |
| 手动粘贴 | 没从这段文字里认出账号或密码 |
| 分享 | 没从分享内容里认出账号或密码，手动填一下 |

抽在一起的好处是：**"认出什么算成功"只有一处判断**（`hasCredential`——
账号或密码至少有一个；只认出网址不算）。如果三个入口各自判一次，
迟早出现"分享说认不出、粘贴却认了"的怪事。

## 7. 验证

### 手动粘贴

1. 新建条目 → 点右上「手动粘贴」
2. 在输入框长按 → 粘贴（用系统菜单，不要用本应用的按钮）
3. 粘贴 `账号：testuser 密码：abc123` → 点「识别」
4. 标题/账号/密码三栏应被填上，密码框自动显示为明文（方便核对）

### 分享进入

1. 在浏览器或聊天里选中一段含账号密码的文字
2. 分享 → 选「账号本」
3. 应该直接打开新建页，且已填好；点「保存」即入库

### 重复触发（回归）

1. 分享一次 → 保存 → 回列表
2. 按 Home 切后台 → 从最近任务切回
3. **应该停在列表页**，不该再弹出一个填好的新建页

## 8. 已知限制

| 限制 | 说明 |
|---|---|
| 部分 App 不出现在分享菜单 | 微信/QQ 内的"分享"是自建面板，可能不列第三方应用。这类场景请用「复制 + 手动粘贴」 |
| 分享的是 HTML 富文本 | 部分应用 `EXTRA_TEXT` 带 HTML 标签。识别器会跳过标签行，多数情况仍能认出账号密码，但可能需要手动改一下标题 |
| 手动粘贴框不能直接调系统剪贴板 | 它的输入框就是普通文本框，用户需要长按调出系统菜单。这是刻意的——我们不再去读剪贴板 |
