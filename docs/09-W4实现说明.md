## 2. 详情页：为什么打开时看不到密码

`revealPassword()` 会把密文解成 `CharArray` 放进内存。详情页是"随便看看"的场景 ——
看账号、看网址、看备注、看上次改密码是什么时候。这些都不需要明文密码。

所以规则是：**不点「显示」就不解密**。

代价是用户想抄密码时要多点一下。这个代价必须付，因为另一条路（进页面就解密）
意味着"每次随手翻一下列表都等于把密码搬进内存一次"。

### 2.1 内存清理

所有解出来的 `CharArray` 都挂在 `DisposableEffect` 上：

```kotlin
DisposableEffect(plain) {
    val snapshot = plain
    onDispose { snapshot?.fill('\u0000') }
}
DisposableEffect(history) {
    val snapshot = history
    onDispose { snapshot.forEach { it.fill('\u0000') } }
}
```

数组一换（点显示 / 点隐藏 / 切换条目）就清旧的，页面销毁清最后一个。

**唯一无法清零的是交给剪贴板的那一份。** `ClipData` 只接受 `CharSequence`，
`String` 不可变也不可擦除。这是 Android API 的硬限制，不是遗漏 —— 补偿手段是
下一节的 30 秒自动清除。

### 2.2 历史密码

`passwordHistory(id)` 最多返回 20 条（`VaultRepository.HISTORY_KEEP`），
按 `changed_at DESC` 排。显示成 `#1 #2 …` 加点号，长度按 `pwd.size.coerceIn(6, 16)` ——
不暴露真实长度，避免"点号数量 = 密码长度"这种泄露。

界面上明确写了"历史密码无法回滚成当前密码"。这是刻意的：回滚功能会让
`entry_history` 从"审计线索"变成"可写状态"，而每次回滚都要再写一条历史，
反复回滚会迅速把 20 条窗口挤满。

## 3. 剪贴板：30 秒与"读不到就不清"

```kotlin
fun copySecret(context: Context, label: String, value: String) {
    val appContext = context.applicationContext
    if (!writeClip(appContext, label, value)) return
    mainHandler.postDelayed({
        if (currentClipText(appContext) == value) writeClip(appContext, "", "")
    }, SECRET_CLIPBOARD_TTL_MS)
}
```

两个细节值得说明：

1. **清除前再读一次剪贴板。** 只有内容仍然等于自己写进去的那串才清。
   否则用户在这 30 秒里复制了别的东西（一段文字、一个地址），会被我们一并清掉。
2. **读不到就放弃清除，而不是盲清。** Android 12+ 限制后台应用读剪贴板，
   `primaryClip` 可能返回 null 或抛异常。这种情况下盲清会把用户刚复制的东西删掉 ——
   失败路径宁可偏向"不动用户数据"。

这套逻辑抽成独立文件而不是写在两个页面里，是因为"复制密码"在详情页、历史密码、
生成器页、编辑页已有四处，规则放在一处才不会漏。

## 4. 生成器：为什么字符集这么小

### 4.1 去掉 `l I 1 O 0`

这些密码经常要：

- 人眼读一遍再手输（智能电视、游戏机、车机）
- 抄在纸上
- 念给别人

`l` 和 `1` 和 `I`、`O` 和 `0` 在这些场景里就是错误来源。少五个字符让池从 74 降到 69，
20 位的熵从 123.4 bit 降到 122.2 bit —— 降了 1 bit，换掉一整类"输错登录失败"。

### 4.2 符号只留 `!@#%^&*-_=+?`

不含：引号、反斜杠、空格、`$`、反引号。

理由：这些在 shell 里要转义，在不少网站后端会被静默过滤 ——
过滤之后你存的和网站收到的就不是一个密码了，而下次登录你还得用存的这个去试。

### 4.3 为什么注入随机源

```kotlin
fun interface RandomSource { fun nextInt(bound: Int): Int }
object SecureSource : RandomSource { /* SecureRandom */ }
```

生产用 `SecureSource`。单测塞固定源，才能写"给定同样的随机序列，两次输出必须相同"
这种确定性断言。否则"生成两次不一样"只能靠概率验证，偶尔会假失败。

这是这个工程里唯一一处"为可测性让步"的设计，代价是 `generate` 多一个默认参数。

### 4.4 全部关掉时的兜底

`Options.normalized()` 在四类全关时**退回仅小写**，而不是抛异常：

```kotlin
return if (c.lower || c.upper || c.digits || c.symbols) c else c.copy(lower = true)
```

UI 层还有一道：`toggle()` 不允许把最后一类关掉（点掉看起来没反应）。
两道防线都留着 —— UI 是给人看的，`normalized()` 是给代码兜底的。

## 5. 回收站：软删除的边界

### 5.1 30 天怎么算

```kotlin
val deadline = deletedAt + VaultRepository.TRASH_RETENTION_MS
val days = if (left <= 0) 0 else ((left + DAY_MS - 1) / DAY_MS).toInt()
```

**向上取整**。剩 0.3 天要显示"还剩 1 天"，不能显示"还剩 0 天" ——
后者看起来像已经过期但还躺在列表里，用户会以为清理坏了。

### 5.2 到期清理的时机

`purgeExpiredTrash()` 在"打开回收站"时跑一次（且只在首次进入跑，
手动刷新不跑）。没有用 `WorkManager`：这是一个打开频率极低的页面，
用户不打开就说明不需要看到清理结果，多一个后台任务只是多一份耗电和一份出错面。

### 5.3 彻底删除为什么逐条做

`purgeAllTrashed()` 逐条调 `purge(id)`，而不是一条 `DELETE FROM entries`：

```kotlin
val trashed = db.entryDao().loadTrashed()
for (row in trashed) db.entryDao().purge(row.id)
```

理由：走 DAO 的 `purge` 才能让 `entry_history` / `custom_fields` / `site_mappings`
的 `ON DELETE CASCADE` 按 SQLite 的正常路径生效；同时能写一条审计
（只记条数，不记内容）。批量 SQL 少几十毫秒，但绕过了外键路径。

「清空」和「彻底删除」都有 `AlertDialog` 二次确认 —— 物理删除之后
连密码历史都找不回来。

## 6. 导航：还是状态机

W4 之后屏幕从 4 个变成 6 个（解锁 / 列表 / 详情 / 编辑 / 待确认 / 回收站 / 生成器），
仍然没有引入 Navigation-Compose：

```kotlin
private sealed interface Screen {
    data object List : Screen
    data object Pending : Screen
    data object Trash : Screen
    data object Generator : Screen
    data class Detail(val entryId: String, val reloadKey: Long = 0L) : Screen
    data class Edit(val entryId: String?, val fromDetail: Boolean = false) : Screen
}
```

两个新参数解决了两个具体问题：

- **`Detail.reloadKey`**：从编辑页保存后回到详情页，`entryId` 没变，
  `LaunchedEffect(entryId)` 不会重跑，页面还显示旧数据。所以回跳时带一个
  `System.currentTimeMillis()` 当 key。
- **`Edit.fromDetail`**：决定保存后去哪。从列表点"新建"进来的，保存后回列表
  （新条目还没有任何详情可看，强行跳过去很怪）；从详情点"编辑"进来的，保存后回详情。
  另配 `EntryEditScreen.onDeleted` —— 删除后详情页已经不存在，必须回列表。

## 7. 静态审查修掉的问题

本机没有 JDK / Gradle / Android SDK（`java -version`、`gradle -v` 均无输出，
`ANDROID_HOME` 为空，出网也被拦），所以下面这些是**读代码**发现的，不是编译器报的。

| 问题 | 后果 | 修法 |
| --- | --- | --- |
| 在局部函数 `fun sep()` 里调用 `HorizontalDivider` | Compose **不允许**在普通局部函数里调用 composable，编译不过 | 把备注/动态码/自定义字段三块显式展开，各自判断"后面还有内容才加分割线" |
| `"•".repeat(String(pwd).length…)` | 为取长度造了一个不可清零的 `String` | 改 `pwd.size` |
| `onDeleted?.invoke() ?: onDone()` | `Unit?` 与 `() -> Unit` 类型不匹配，编译不过 | 改 `if (onDeleted != null) onDeleted() else onDone()` |
| `EntryListScreen` 的 `collectAsState` 直接吃 `repo.observeSummaries()`（W3 遗留隐患） | 每次重组新建 Flow，造成反复取消/重订阅 | `remember(repo) { repo.observeSummaries() }` |

## 8. 真机验证（约六分钟）

| # | 动作 | 期望 |
| --- | --- | --- |
| 1 | 列表右上 `⋮` → 生成密码 | 出现 20 位密码，底部"约 122 bit · 很强" |
| 2 | 拖长度到 8 | 密码立刻变 8 位，熵掉到约 49 bit |
| 3 | 关掉大写、数字、符号 | 每关一类密码立刻重生成，且不含该类字符 |
| 4 | 试图关掉最后一类 | 点不动（不会崩） |
| 5 | 点复制 → 去别处粘贴 | 粘到的是密码；**30 秒后再粘贴，剪贴板已空** |
| 6 | 列表点一条 → 详情 | 密码显示为点号；点「显示」才出现明文 |
| 7 | 详情点「查看历史密码」 | 列出最多 20 条，每条可复制 |
| 8 | 详情 → 编辑 → 改标题 → 保存 | 回到详情，**标题已经是新的**（验证 `reloadKey`） |
| 9 | 详情 → 删除 | 回列表，该条消失；进回收站能看到，显示"还剩 30 天" |
| 10 | 回收站点「恢复」 | 回到列表；再进回收站已空 |
| 11 | 回收站点「清空」 | 弹确认框；确认后列表清空 |

### 排查表

| 现象 | 原因 |
| --- | --- |
| 复制后 30 秒剪贴板没清 | Android 12+ 读剪贴板受限，读不到就放弃清除（设计如此） |
| 编辑保存后详情页还是旧数据 | `reloadKey` 没传或没变化 |
| 详情点编辑后再按返回，回到列表而不是详情 | `fromDetail` 传到 `Edit` 时的值不对 |
| 回收站天数显示为 0 天 | `remainingText` 的向上取整被改掉了 |
| 生成器一拖滑杆就卡 | `LaunchedEffect(options)` 里做了重活（正常应只有一次 `SecureRandom`） |
