# 1.9：把「结构化」的几种粘贴形状全部认下来

## 起因

1.8 之后用户拿来六段真实粘贴，全部认不出来或认错（原文六条）：

1. 外面包着一层的 JSON —— `{"accounts": [{"site": "Steam", "user": "demo_steam01", "pass": "St@123456", "note": "游戏"}, …]}`
2. XML —— `<accounts><account><platform>微信</platform><user>wx_xml_demo</user><pass>Wx@123456</pass></account>…</accounts>`
3. 括号包值 —— `平台(淘宝) 账号(taobao_bracket) 密码(Tb@123456)`，标题被认成「平台(京东）」
4. 查询串 —— `platform=微博&account=weibo_param&password=Wb@123456&note=参数测试`，`&` 被粘进密码
5. 账号密码上下交替 —— `demo_mail01@example.com` / `Mail@123456` / `demo_mail02@example.com` / `Mail#654321` 四行认成一条
6. 同行混用分隔符 —— 分号、竖线、逗号三种写法混在一起，三条认成一条

六条的共同点是"结构是清楚的，只是识别器只认自己熟悉的那一种写法"。1.7 已经认表格（同一种分隔符、有表头）、认 JSON 数组（顶层就是数组），但外面多包一层、换个容器、换个分隔符就全部掉回"按位置猜"。

## 改了什么

`app/src/main/java/com/yg/vaultbook/core/util/CredentialParser.kt`：

### 字段名表

- `PASS_LABELS` 补 `pass`。JSON 里 `"pass"` 是最常见的短键名，原来只认 `password`/`passwd`/`password`/`pwd`，第 1 条里两个对象的密码于是全空。`pass` 放在最末，因为正则的交替分支是先试长的分支，`password`、`passwd`、`passcode` 都比它长，不会被它抢走。
- `cleanValue()` 的 trim 集合加 `&`。查询串里 `password=Wb@123456&note=参数测试` 的值截到 `&` 就结束，不剥掉会得到 `Wb@123456&`。

### 四条新通道（按识别顺序排在表格与 JSON 旁边）

1. `xmlRecords` —— 用第一个标签名当切块锚点：同名字段再次出现就是下一条。字段名走 `columnOf`，所以 `<platform>` 进标题、`<url>` 进网址、`<note>` 进备注。要求至少两条才接管，单条仍走普通流程，免得把网页里随便一段 `<div>` 当凭据。
2. `parenRecords` —— `标签(值)`、`标签（值）`，半角全角都认。要求一行里至少两个括号对、并且认出了密码才收：`平台(必填) 账号(必填)` 是表单说明，不收。
3. `labeledRows` —— 行首是列名、后面按位置排。分隔符在 `| , ， ; ； 制表符 &` 里挑，取"切得最碎"的那个（切出的段数最多），所以同一段文字里三种写法混着也能逐行各自归位。第一个单元格自己写成 `列名=值` 时直接归位，不吃位置。
4. `alternatingRecords` —— 账号一行、密码一行上下交替。要求至少四行、行数为偶数、奇数位像账号（`ACCOUNT_TOKEN` 或 `EMAIL_SHAPE`）、偶数位像密码（`looksLikeSecret`，带符号或数字且不像邮箱），三条不硬凑。

`ROW_ORDER` 的顺序是 标题 → 账号 → 密码 → 备注 → 网址，**备注故意排在网址前**：`平台|知乎|zhihu_mix|Zh#654321|竖线` 里第五列是"竖线"这种备注，不是网址，把网址排前面会把它认成网址。

### 兜底

`guessFromLeftovers` 两段分支加了 `isLabelSlot`：两段都是「列名(占位说明)」形状时返回空。不做这一步，括号通道因"没有密码"拒收之后，残行猜测会把 `平台(必填)` 当账号、`账号(必填)` 当密码 —— 比认不出来更糟。

## 刻意取舍

- **XML 只认浅层**。`XML_PAIR_REGEX` 是 `<tag>值</tag>` 的单层配对，值里不许再出现尖括号。带命名空间、带 CDATA、带属性的深层 XML 不认 —— 手机备忘录和聊天记录里粘出来的"XML"几乎都是这种一条条平铺的，真遇到复杂 XML 应该导出成 JSON 或 CSV。
- **`&` 只当行内分隔符，不当表格分隔符**。`TABLE_DELIMITERS` 没动，`ROW_DELIMITERS` 才有 `&`。表格是给人看的表格，`&` 是网址参数的连接符，两者语义不同。
- **交替行要求严格偶数**。四行认两条、六行认三条；三行认不出来（奇数），因为无法判断第三行是新一条的账号还是上一条多出来的备注。
- **括号通道必须有密码**。只有账号没有密码的括号串，多半是字段说明。
- **不用 `org.json` 也不用 XML 解析器**。前者在 JVM 单测里是 not mocked 的桩，后者会把"不合法就抛异常"当正常路径。两条通道都是正则加自己切块，可测、可解释。

## 验证

新增 `CredentialParserStructuredTest`，13 个用例覆盖六条原文加反例：外层包着 accounts 数组的 JSON、裸 pass 键、浅层 XML、XML 里的备注与网址、括号包值、全角括号、括号里只有列名说明时不认、查询串里的 amp 不进密码、账号密码上下交替、三行交替不硬凑、同行混用分号竖线逗号认三条、表头行不单独成记录、带表头的表格照旧。

全量 29 个测试类 499 个用例 0 失败。六个样本的实测结果：

- 第 1 条：Steam / demo_steam01 / St@123456 / 游戏，Epic / demo_epic@example.com / Ep#654321 / 测试
- 第 2 条：微信 / wx_xml_demo / Wx@123456，QQ / 1000000003 / Qq#654321
- 第 3 条：淘宝 / taobao_bracket / Tb@123456，京东 / jd_bracket@example.com / Jd#654321
- 第 4 条：微博 / weibo_param / Wb@123456 / 参数测试，知乎 / zhihu_param / Zh#654321
- 第 5 条：demo_mail01@example.com / Mail@123456，demo_mail02@example.com / Mail#654321
- 第 6 条：微博 / weibo_mix / Wb@123456 / 分号，知乎 / zhihu_mix / Zh#654321 / 竖线，B站 / bili_mix / Bili@123456 / 逗号

## 还没做

- 深层嵌套 XML（`<list><item>` 之外的再套一层）、带属性的 XML。
- 一条里同时出现"账号密码"和"手机号验证码"时，验证码会被当密码。这需要另一个字段类型，目前没有。
- 密钥/令牌类（纯长串无分隔）仍然不认，避免把一段哈希当密码收进来。
